## 一、同一支腳本內,多個步驟修改同一個檔案時的順序依賴

### 問題重現(`update42.sh` 實際踩坑)

`update42.sh` 內部依序執行:

1. 第 1 步:全專案 `grep -rl "@/api/ledger'"` → 取代成 `@/api/ledgerApi'`,**這一步已經改到了 `TransactionList.vue` 的 import 路徑**
2. 第 7 步:對 `TransactionList.vue` 做精確字串比對,但比對字串裡**仍然寫著改名前的 `'@/api/ledger'`**

腳本執行到第 7 步時,檔案早就不是「原始內容」了,字串當然對不上,`raise SystemExit` 中止,且**中止點之後的 `git commit` 永遠不會執行到**。

### SOP 補強

撰寫涉及**多個步驟修改同一份檔案**的腳本時:

1. 先列出「這份檔案會被本腳本改動幾次」,依執行順序排列
2. 每一步的比對字串(`old`),都要以「前面步驟執行完之後」的狀態為準,不是原始檔案內容
3. 若某一步的修改是「全域掃描 + 取代」(例如 rename 後更新所有 import 路徑),而後面還有針對**同一批檔案**的精確修改,寫腳本前**先在腦中(或紙上)完整跑一次前面步驟會產生的中間狀態**,再依中間狀態撰寫後面的比對字串

## 二、每支腳本開頭固定加入「前置驗證」,確認依賴的前一支腳本已套用

### 問題

`update-deploy-sop-20260708.md` 已經提過「多支 `updateN.sh` 互相依賴時,精確比對會自動偵測前一支是否套用過」,但這只在**踩坑之後排查時**才會發現。這次(`update44.sh`/`update45.sh`)改成**開頭主動檢查**,不用等到後面的精確比對失敗才知道。

### 固定寫法

```bash
# ---------- 前置檢查:確認上一支腳本的改動已存在 ----------
if ! grep -q "<上一支腳本會留下的特徵字串>" "<受影響的檔案路徑>"; then
  echo "❌ 尚未包含上一支腳本的改動,請先確認上一支腳本是否已成功套用" >&2
  exit 1
fi
echo "✅ 確認上一支腳本的改動已存在,可以繼續套用本次異動"
```

實際套用範例:

- `update44.sh` 開頭檢查 `TransactionList.vue` 是否已有 `AccountFilterPicker from './AccountFilterPicker.vue'`(`update43.sh` 應留下的痕跡)
- `update45.sh` 開頭檢查 `TransactionList.vue` 是否已有 `advanced-filter-panel`(`update44.sh` 應留下的痕跡)

**效果**:若前一支腳本其實沒套用成功(例如中途中止、忘記 commit、被 `deploy.sh` 蓋掉),本腳本會在**寫入任何檔案之前**就直接中止並給出明確訊息,不會疊加在錯誤的版本上、產生更難排查的中間狀態。

## 三、`git reset --hard` 不會清掉「未追蹤的新檔案」,重跑腳本時要當作可能殘留處理

### 問題重現

`update42.sh` 在第 7 步中止前,已經：

- 用 `git mv` 改名 `api/ledger.ts` → `api/ledgerApi.ts`(git 已追蹤的異動)
- 修改了 `transactions.py`、`types/ledger.ts`(git 已追蹤的異動)
- 用 `cat >` **新建**了 `TagFilterPicker.vue`、`AccountFilterPicker.vue`(git **從未追蹤過**的全新檔案)

中止後 `git commit` 沒有執行,接著跑了 `deploy.sh` 的 `git reset --hard origin/main`。這個指令**只會還原 git 已追蹤的檔案**,對「從未 `git add` 過的全新檔案」完全不會動——所以最後現場是:

- `api/ledger.ts`、`transactions.py`、`types/ledger.ts` 全部被還原回原始版本
- 但 `TagFilterPicker.vue`、`AccountFilterPicker.vue` 兩個新檔案卻還留著

`git status` 會顯示這兩個檔案是 `Untracked files`,如果沒有意識到這是「半殘留」狀態,重寫修正腳本時可能誤以為「這兩個檔案應該不存在」或「內容應該是乾淨的」而出錯。

### SOP 補強

重跑修正腳本(如 `update43.sh`)時,對於**上一次執行中可能已經新建過的檔案**:

- 一律用 `cat > path << 'EOF' ... EOF` **整份覆寫**,即使猜測內容可能已經一致,也覆寫一次,不要用「先檢查是否存在」的條件邏輯去猜測是否需要建立
- 不要假設「腳本中止 = 完全沒有任何改動殘留」,要按照「已追蹤檔案會被 `reset --hard` 還原、未追蹤檔案不會」這個實際行為去推斷現場狀態

## 五、後續可考慮事項

1. 若未來 `updateN.sh` 對同一檔案的修改步驟持續增加,可考慮把「這份檔案目前被改動到第幾步」的中間狀態,以註解方式寫在每個 python heredoc 區塊上方,方便日後回溯排查,而不是只能重新在腦中推導一次
2. 前置驗證目前是每支腳本手動加一段 `grep` 判斷,若腳本數量持續增加,可評估是否要建立一個共用的「腳本相依性宣告」慣例(例如檔頭固定寫 `# DEPENDS_ON: update44.sh`),但目前規模每支手動加 `grep` 判斷的成本還不高,先不列入本次範圍
3. 本次「孤兒檔案」問題屬於 `git reset --hard` 的既有行為特性(對 untracked 檔案無效),而非工具或腳本本身的 bug,未來若想更徹底避免半殘留狀態,可考慮讓 `deploy.sh` 執行前先 `git status --porcelain` 檢查是否有 untracked/modified 檔案並警示,而不是直接 `reset --hard`,但這會改變既有 `deploy.sh` 的行為,需另外評估是否要調整

## 六、SOP 總結(累加自前三版)

1. 動手寫 `updateN.sh` 前,一律先看過所有要改動的檔案目前實際內容
2. 改動範圍大 → 完整覆寫;改動範圍小 → `python3` 精確字串比對,對不上直接中止
3. 有無法直接確認的假設,腳本內加前置驗證,驗證不過不寫入任何檔案
4. **(本次新增)** 同一支腳本內若對同一檔案有多個修改步驟,後面步驟的比對字串要以「前面步驟執行完之後」的狀態為準,不能假設是原始內容
5. **(本次新增)** 每支腳本開頭固定檢查前一支依賴腳本的改動是否已存在,對不上就直接中止並提示,不寫入任何檔案
6. 執行完 `updateN.sh` 後,務必 `git log --oneline -1` 確認 commit 真的產生(建議直接寫進腳本結尾自動印出,不用每次手動下指令)
7. **(本次新增)** 重跑修正腳本時,對於上一次執行可能已建立的全新檔案,一律用完整覆寫處理,不要假設它們不存在或內容乾淨(`git reset --hard` 不會清掉 untracked 檔案)
8. 每支腳本都附上明確的「驗證重點」清單給使用者核對
9. bug 回報描述含糊時,先問清楚操作路徑,不要先動手改
10. 功能驗證通過後,補一份格式一致的 md 文件記錄決策脈絡
11. 每支腳本開頭固定執行「自動歸檔」,且與功能異動分開 commit
12. `push` 與 `deploy.sh` 執行步驟刻意保留手動確認,不做自動化串接
