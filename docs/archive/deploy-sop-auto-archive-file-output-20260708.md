## 一、自動歸檔:每支腳本開頭固定執行,且獨立 commit

### 設計原則

- 歸檔動作(把非本次執行編號的 `update*.sh` 搬進 `updateN/` 資料夾)是「整理」,跟本次的 `feat:`/`fix:` 是不同性質的異動,**不應該混在同一個 commit**
- 若混在一起,`git log` 之後回溯「某個功能是哪次改的」會被檔案搬移的雜訊淹沒(`update36.sh` 首次套用時就發生過:一次 commit 裡混了 2 個 zip 刪除 + 24 支腳本搬移 + 實際功能程式碼)
- 因此固定寫法是:歸檔 → 若有變動就先產生一個 `chore:` commit → 才繼續本次功能異動的程式碼修改與 `feat:`/`fix:` commit

### 固定寫法(放在每支 `updateN.sh` 最前面)

```bash
# ---------- 0. 自動歸檔:把小於當前編號的 updateM.sh 搬進 updateN/ ----------
mkdir -p updateN
CURRENT=<本次腳本編號>
for f in update*.sh; do
  [ "$f" = "update${CURRENT}.sh" ] && continue
  [ -f "$f" ] || continue
  git mv "$f" "updateN/$f" 2>/dev/null || mv "$f" "updateN/$f"
done
git add -A
if ! git diff --cached --quiet; then
  git commit -m "chore: 歸檔已執行的 updateN.sh 腳本"
  echo "✅ 歸檔 commit 已產生(與本次功能改動分開)"
fi
```

### 效果

- `git log --oneline` 會清楚看到 `chore: 歸檔已執行的 updateN.sh 腳本` 與 `feat:`/`fix: ...` 是兩個獨立 commit
- 不需要使用者再手動 `mv`/整理資料夾,每次執行完當次腳本,舊腳本就自動歸位

## 二、自動產出腳本檔案,取代手動複製貼上存檔

### 問題

舊流程是 Claude 在對話裡貼出完整 `updateN.sh` 內容,使用者需要:
1. 手動全選複製
2. 在 server 上 `cat > updateN.sh << 'EOF'` 貼上
3. 確認貼上完整、沒有截斷或誤觸格式跑掉

這個手動搬運步驟本身沒有直接產生過 bug,但每次都要重複操作,且是額外的人工步驟。

### 改善方式

之後 Claude 產出 `updateN.sh` 時,直接建立實體檔案並提供下載連結,使用者流程改為:
1. 從對話下載 `updateN.sh`
2. 傳到 server(例如 `scp`,或使用者慣用的檔案傳輸方式)
3. `chmod +x updateN.sh && ./updateN.sh` 直接執行

**不影響**腳本本身的內容與既有 SOP(完整覆寫 vs 精確字串替換的選擇準則、前置驗證、依賴聲明等,皆沿用 `update-deploy-sop-20260708.md` 既有規則),只改變「腳本內容如何交付給使用者」這個環節。

### 例外情況

若腳本內容需要根據使用者回報的 server 端實際檔案內容即時調整(例如字串比對用的 `old` 內容),仍會先在對話中說明修正邏輯,產出的檔案版本會是最終確認後的版本,避免下載到還需要再次修改的中間版本。

## 四、後續可考慮事項

1. 若 `updateN/` 資料夾內腳本數量持續增加,可評估是否需要定期(如每 20 支)再往下依日期分子資料夾,避免單一資料夾檔案過多
2. 目前歸檔判斷邏輯是「檔名不等於當前編號就搬移」,若未來有需要保留最近 N 支腳本在根目錄方便快速查閱(而非全部搬空),可調整迴圈條件,目前先維持「執行完立刻歸檔」的簡單規則
3. 自動產出腳本檔案後,若使用者的下載/傳輸環境有限制(如無法直接下載檔案到 server 所在網路),仍可退回原本的貼上存檔方式,兩種交付方式並不互斥
