# 功能新增:交易紀錄消費品項篩選 + 篩選 UI 改為進階篩選面板

建立日期:2026-07-10

## 一、背景與需求

1. 交易紀錄無法依「消費品項(Tag)」篩選,只能依日期/帳戶/分類/金額範圍篩選
2. 原本帳戶篩選是原生 `<select>` 下拉選單,不好操作;分類篩選(`CategoryFilterPicker.vue`)已是按鈕式,但體驗不一致
3. 篩選欄位持續增加後,若全部塞在同一行篩選列會太擠

## 二、討論與決策

### 消費品項篩選的 OR/AND 語意

一筆交易可掛 0~多個消費品項(多對多),篩選時「同時勾選多個品項」採 **OR 語意**:交易只要掛了其中任一個被選取的品項就列入,不要求同時掛滿所有勾選的品項。理由:AND 語意在使用情境上較少見,且實作需要額外的 `HAVING COUNT(DISTINCT tag_id) = 選取數量` 邏輯,複雜度不成比例。

### 篩選列版面配置

篩選欄位一多,若全部展開會太亂(尤其分類/消費品項數量多時)。最終決策:

| 項目 | 決定 |
|---|---|
| 日期區間、金額區間 | 維持在主篩選列,永遠可見 |
| 帳戶 / 分類 / 消費品項 | 收合進「進階篩選」按鈕,點擊才展開;按鈕上會顯示目前已套用幾項(例如「進階篩選（2）」) |

### 帳戶 / 分類 / 消費品項三者展開後的呈現方式,各自不同

三者資料特性不同,套用同一種 UI 反而互相打架,最終依各自特性分開設計:

| 欄位 | 呈現方式 | 原因 |
|---|---|---|
| 帳戶 | 搜尋框 + 攤開全部按鈕 | 選項數量少,攤開不會亂 |
| 分類 | 逐層鑽取麵包屑(比照既有 `CategoryPicker.vue`) | 分類有階層結構,且既有分類數量已達 80+,攤開全部完整路徑會非常雜亂;搜尋框仍保留,可跨層級直接跳轉 |
| 消費品項 | 「最近使用」(前 8 個)+「全部品項」兩區(比照既有 `TagPicker.vue`) | 品項無階層結構,無法比照分類做鑽取,改用「最近使用優先顯示」降低單次視覺負擔;搜尋時收斂為單一清單 |

這個決策經過三次調整才定案(第一版做成「點按鈕彈出小面板」,第二版改成「全部一直攤開」,使用者反映太亂後,才改成本節的最終版本)。

## 三、後端變更

### 修改檔案

| 檔案 | 異動內容 |
|---|---|
| `app/routers/transactions.py` | `list_transactions` 新增 `tag_ids: list[str] \| None` 查詢參數;篩選邏輯 `join TransactionTag` + `filter(tag_id.in_(...))` + `.distinct()`(避免一筆交易同時符合多個篩選品項時被重複列出) |

### 技術重點

- OR 語意 + `distinct()`:交易掛的品項只要符合任一個篩選條件就列入,同時避免 JOIN 造成的重複列
- 沒有新增 schema(篩選是 query 參數,不是 body),不影響既有 `TransactionCreate`/`TransactionUpdate`

## 五、Bug 修復紀錄(本次上線過程實際踩坑)

### 1. axios 陣列參數序列化格式與後端 FastAPI 不一致

| 項目 | 內容 |
|---|---|
| 現象 | 若沿用 `apiClient.get('/transactions', { params: filters })` 直接把 `tag_ids` 陣列傳給 axios,後端完全收不到篩選效果 |
| 原因 | axios 預設把陣列序列化成 `tag_ids[]=a&tag_ids[]=b`,但 FastAPI 的 `Query(list[str])` 預期的是重複 key `tag_ids=a&tag_ids=b`,兩種格式不相容 |
| 修正 | `fetchTransactions` 改用 `URLSearchParams` 手動組 query string,`tag_ids` 用 `params.append('tag_ids', id)` 逐一附加,確保格式與後端一致 |

### 2. 篩選 UI 版面反覆調整

| 項目 | 內容 |
|---|---|
| 現象 | 第一版「點按鈕彈出小面板」測試通過,但使用者後續希望改成「像分類管理頁一樣搜尋框+攤開按鈕」;第二版「全部一直攤開」上線後,使用者反映分類/品項數量多時太亂 |
| 修正 | 最終收斂為第二節「呈現方式」表格的分工設計:帳戶攤開、分類改回逐層鑽取麵包屑、消費品項改為最近使用/全部品項分區 |
| 教訓 | UI 呈現方式的決策,建議在動手寫程式前先確認具體版面配置(例如「攤開後佔用空間可否接受」「各欄位資料特性是否適合同一種呈現方式」),避免像本次一樣來回調整三次;已在 `update-deploy-sop-20260710.md` 記錄的腳本流程教訓之外,額外記錄這點供未來功能開發參考 |

## 七、後續可考慮事項

1. 目前消費品項篩選為 OR 語意,若未來有「必須同時掛滿所有勾選品項」(AND 語意)的需求,需要額外設計 `HAVING COUNT(DISTINCT tag_id) = 選取數量` 或改用子查詢,屬於較大工程,先不列入本次範圍
2. 分類篩選目前仍是「精確符合單一分類」(不含子分類),若未來想要「篩選某大類時,連同底下所有子分類的交易都列入」,需要額外設計遞迴查詢,是語意上的取捨,不是本次的 bug
3. 「進階篩選」目前是單一收合區塊,若未來篩選欄位持續增加,可評估是否需要分頁籤(而不是全部塞進同一個展開面板)
