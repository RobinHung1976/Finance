## 一、背景

逐檔貼路徑覆蓋容易漏檔、貼錯位置。改用 `updateN.sh`(本機執行,覆寫檔案 + `git commit`)取代逐檔手動修改,`push`/`deploy` 保留手動確認,不做自動化串接。

## 二、動手寫腳本前的固定第一步:先看檔案,不要憑記憶

**不可以**依賴之前版本的印象或聊天紀錄裡貼過的舊內容來寫 `updateN.sh`,尤其該檔案如果最近有其他異動。

- 每次要修改一個檔案,**一律先要求取得該檔案目前的實際內容**(`view`/`cat`),再動手寫覆寫或字串比對的腳本
- 這不是「腳本中止後才做的補救」,而是**動手寫之前的必經步驟**;`bug-fix-20260707-household-name.md` 記錄的坑,就是先寫腳本、字串比對失敗才回頭要內容,應該反過來
- 若一個功能牽涉多個檔案(前端 + 後端 + 型別定義),**全部檔案都要先看過**,不要漏看關聯檔案(例如只看 `TagList.vue` 卻沒看 `types/ledger.ts` 裡對應的介面定義)

## 三、腳本撰寫方式

### 命名規則(沿用舊版)

| 項目 | 規則 |
|---|---|
| 檔名 | `updateN.sh`,N 遞增(`update1.sh`, `update2.sh`, ...) |
| 存放位置 | repo 根目錄,與 `deploy.sh` 平級 |
| commit message | `feat:` / `fix:` 前綴 + 本次異動摘要 |

### 完整覆寫 vs 精確字串替換:怎麼選

| 情境 | 用法 |
|---|---|
| 整份檔案的邏輯都有大幅改動(新增功能、改版面結構) | `cat > path << 'EOF'` **完整覆寫**,不要用字串比對硬湊,片段比對容易漏掉上下文關聯 |
| 只想動檔案裡一小段(例如一個 interface 多一個欄位、一個 prop 定義),其餘完全不動 | `python3` heredoc **精確字串比對替換**,`old` 找不到就直接 `raise SystemExit` 中止,不要用 `sed`(對特殊字元易誤判) |

判斷原則:**改動範圍如果超過檔案一半以上內容,直接整份覆寫;只是加一兩行,才用精確比對**,避免精確比對的 `old` 字串太長、太容易對不上。

### 依賴其他 updateN.sh 的處理方式

如果這支腳本的改動,是建立在**前一支腳本已經套用**的假設上(例如這次改的欄位,是前一支才剛新增的):

1. 腳本開頭或訊息裡**明確聲明**:「此腳本假設 updateN-1.sh 已經套用」
2. 若透過 `python3` 精確比對寫入,比對的 `old` 字串本身就會**自動偵測**前一支是否套用過(對不上就中止,並在錯誤訊息裡提示「可能是 updateN-1.sh 尚未套用」),不需要額外寫檢查邏輯

### 無法直接確認的假設(如 DB 欄位名稱),要在腳本內加前置驗證

如果腳本的邏輯建立在某個**沒有檔案可以直接核對**的假設上(例如 ORM 欄位名稱、關聯表結構),不要盲目假設,在腳本最前面加一段**前置驗證**,驗證不過就直接中止、不寫入任何檔案:

```bash
# ---------- 前置檢查:確認假設的欄位名稱存在 ----------
cd "$BACKEND"
source venv/bin/activate
python3 -c "
from app.models import SomeModel
cols = SomeModel.__table__.columns.keys()
assert 'expected_column' in cols, '❌ 欄位名稱與假設不符,請人工確認並修改腳本'
print('✅ 欄位名稱符合預期')
"
deactivate
cd ..
```

之後如果拿到 `models.py` 等實際檔案確認過假設無誤,可以把這段前置檢查拿掉,但**在確認之前不要省略**。

## 四、執行步驟(每次異動固定流程,新增第 2.5 步)

```bash
# 1. 本機 repo 根目錄
chmod +x updateN.sh && ./updateN.sh

# 2. 確認 diff
git diff HEAD~1 --stat

# 2.5【本次新增,務必執行】確認 commit 真的成功產生
git log --oneline -1
# 若腳本中途因某個字串比對失敗而以 set -euo pipefail 中止,commit 那一行永遠不會被執行到,
# 但終端機不一定會有醒目的錯誤訊息;只看「有沒有印出錯誤字」會誤判成功。
# 務必用這一步實際確認 HEAD 是新的 commit,而不是還停在上一次的版本。

# 3. push(腳本內故意不含此步,避免誤觸發部署)
git push origin main

# 4. server 端部署(注意:若已在 server shell 內,不需再 ssh 進自己)
cd /root/apps && ./deploy.sh

# 5. 瀏覽器強制重整清快取
# Ctrl+Shift+R
```

**這一步的教訓來源**:`household-management-20260708.md` 記錄過 `update29.sh` 靜默失敗、`git commit` 從未跑到,且被下一次 `deploy.sh` 的 `git reset --hard` 蓋掉痕跡,是同一類坑第二次發生。這份 SOP 之前沒有把這個教訓寫進「執行步驟」,只留在個別 bug 修復紀錄裡,這次補上。

## 五、每支腳本都要附上明確的「驗證重點」

腳本執行、push、deploy 完成後,不要只說「測試看看」,要**條列具體的驗證項目**,例如:

- 某個畫面應該出現什麼新元素
- 某個操作應該觸發什麼結果
- 特別容易被改動波及、但這次**不應該受影響**的既有功能(回歸測試項目)

讓使用者驗證時有明確的checklist可以逐項核對,而不是憑感覺看一眼。

## 六、常見錯誤與排查(沿用舊版,補充第 4 點)

| 現象 | 原因 | 對策 |
|---|---|---|
| `chmod: cannot access 'updateN.sh'` | 腳本內容直接貼進終端機執行,未存成檔案 | 用 `create_file`/`cat > updateN.sh <<'EOF'` 先存檔再 `chmod +x` |
| `ssh finance-server` 要求密碼且失敗 | 已在該台 server shell 內,不需再 ssh 進自己 | 確認 prompt 是否已是 `root@finance-server`,是則直接 `cd /root/apps && ./deploy.sh` |
| 500 / 版面異常修正後又復發 | 先前是直接在 server 上 `sed` 改檔案,未進版控,被 `deploy.sh` 的 `git reset --hard` 蓋掉 | 一律走本機 repo 改 → commit → push → server deploy,禁止在 server 上手動改程式檔案 |
| `python3` heredoc 印出 `❌ ... 不符` | 目標檔案實際內容與腳本假設的舊字串不一致(可能先前手動改過,或依賴的前一支 `updateN.sh` 尚未套用) | 貼目前檔案內容,重新產生對應 updateN.sh;若是依賴前一支腳本,先確認前一支是否已跑過 |
| 腳本印出的錯誤訊息看起來正常,但功能實際沒生效 | 只看終端機輸出、沒有實際確認 `git log`,腳本可能中途中止 | 依第四節第 2.5 步,每次都用 `git log --oneline -1` 確認 |

## 七、收到 bug 回報但描述含糊時,先問清楚操作路徑,不要先動手改

同一個畫面上可能有好幾個相似的互動元件(例如「逐層鑽取選項按鈕」vs「搜尋結果列表」vs「改名按鈕」),使用者的描述如果不夠具體(例如只說「點了不能修改」),**先確認使用者實際點的是哪個元件**,再決定要不要改程式。

- 好處:避免對著沒問題的地方亂改,反而把原本正常的邏輯改壞
- 若使用者後續確認「是我測試錯地方,可以忽略」,代表這個確認步驟是必要的,省下一次不必要的程式異動

## 八、功能驗證通過後,補一份對應的 md 文件

跟 `deploy.sh` 本身無關,但這是本次額外發現值得固定下來的收尾習慣:每個功能改善(不只是新功能,UX 調整/bug 修復也算)在**驗證通過後**,補一份跟現有文件庫格式一致的 md(建立日期、背景與需求、討論與決策、修改內容、目前狀態、後續可考慮事項),方便日後回溯「當初為什麼這樣設計」。

- 檔名沿用既有慣例:`{領域}-{功能簡述}-{日期}.md`
- 不需要在功能開發過程中邊做邊寫,**驗證通過、確定不會再改之後**再整理一次即可,避免中途變動導致文件要一直重寫

## 九、SOP 總結

1. 動手寫 `updateN.sh` 前,**一律先看過所有要改動的檔案目前實際內容**,不依賴記憶或聊天紀錄裡的舊版本
2. 改動範圍大 → 完整覆寫(`cat >`);改動範圍小 → `python3` 精確字串比對,對不上直接中止
3. 有無法直接確認的假設(如 DB 欄位名稱),腳本內加前置驗證,驗證不過不寫入任何檔案
4. 多支 `updateN.sh` 有相依關係時,明確聲明依賴,並讓精確比對自動偵測前一支是否已套用
5. 執行完 `updateN.sh` 後,**務必 `git log --oneline -1` 確認 commit 真的產生**,不能只看終端機有沒有印出錯誤字樣就假設成功
6. 每支腳本都附上明確的「驗證重點」清單給使用者核對
7. bug 回報描述含糊時,先問清楚操作路徑,不要先動手改
8. 功能驗證通過後,補一份格式一致的 md 文件記錄決策脈絡
9. `push` 與 `deploy.sh` 執行步驟刻意保留手動確認,不做自動化串接
